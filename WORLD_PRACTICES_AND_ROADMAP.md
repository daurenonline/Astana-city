# Мировые практики и предложения по развитию «Контур региона»

Документ отражает обзор лучших мировых решений в области управления инфраструктурными проектами (Procore, Oracle Aconex, Kahua, PMI/EVM, ISO 21500, Building Information Modeling / Common Data Environment) и конкретные предложения по доработке.

---

## 1. Что уже реализовано в прототипе

- **ГИС-карта (OpenStreetMap/Leaflet)** с цветовым «светофором» объектов.
- **EVM-анализ в реальном времени** для каждого выбранного объекта: SPI, CPI, EV%, EAC, прогноз.
- **Per-project журнал событий (History & Audit)** с фильтрами по типам:
  - штабы и совещания (с указанием руководителя);
  - выездные проверки технадзора;
  - встречи/разборы с подрядчиком;
  - выданные предписания;
  - оплаты и акты (КС-2);
  - обращения граждан (e-Otinish);
  - фотофиксация;
  - переносы сроков и смена статусов.
- **Селекторная справка** для аппаратного совещания акима.

## 2. Мировые практики (как сделано у лидеров)

### 2.1 Common Data Environment (CDE) — единая среда данных
В международных проектах (ISO 19650) вся проектная документация, РД, акты, переписка и фото ведутся в **единой управляемой среде**. Каждый документ имеет статус: *Work in progress → Shared → Published → Archived*.

**Предложение:** добавить в карточку объекта раздел «Документы» со статусами (Черновик / На согласовании / Утверждён / Архив) и журналом версий ПСД.

### 2.2 Meeting minutes с трекингом поручений
В Procore/Aconex протоколы совещаний привязываются к объекту, каждая встреча создаёт **поручения (action items)** с ответственным и сроком.

**Предложение:** в событии типа «Штаб/совещание» добавить под-блок **«Поручения»** (что, кому, срок, статус Выполнено/Просрочено). Это закрывает претензию «поговорили и забыли».

### 2.3 RFI (Request for Information) и Submittals
В мировой практике подрядчик задаёт вопросы через **RFI**, а материалы согласуются через **Submittals**. Просрочка ответа заказчика фиксируется юридически.

**Предложение:** модуль RFI с контролем SLA ответа заказчика (например, 3 рабочих дня). Просроченный ответ заказчика — тоже риск проекта.

### 2.4 Change Orders (допсоглашения) и контроль объёмов
Любое изменение объёма/сметы — отдельная заявка **Change Order** с обоснованием и влиянием на срок/бюджет.

**Предложение:** связать модуль «Deadline Extension Request» с аналогичным «Budget Change Request», чтобы видеть совокупное давление на бюджет.

### 2.5 EVM по стандарту PMI (ANSI/EIA-748)
Полноценный EVM оперирует: PV, EV, AC, SV, CV, SPI, CPI, EAC, ETC, VAC, TCPI.

**Предложение (следующий шаг):**
- добавить **VAC (Variance at Completion)** = BAC − EAC;
- **TCPI** (индекс необходимой эффективности для сдачи в бюджет);
- **прогноз даты сдачи** по SPI (Date Forecast);
- график **S-кривой** (накопительно PV vs EV vs AC по неделям).

### 2.6 Риск-реестр с вероятностью и влиянием (Risk Register)
В мировой практике риск = *вероятность × влияние*, с владельцем риска и планом реагирования (PMI).

**Предложение:** превратить текущий «Топ-риск» в полноценный **Risk Register**: оценка 1–5 по вероятности и влиянию, тепловая карта рисков, владелец риска, статус (Открыт/Снят/Реализовался).

### 2.7 Фото/видео- и геофиксация, дроны
Стандарт мировых решений — **ежемесячная аэрофотосъёмка (дрон)** с привязкой ортофотопланов к ГИС для контроля объёмов.

**Предложение:** заложить в дорожную карту регулярную аэрофотосъёмку с наложением на карту (WebODM + GeoJSON).

### 2.8 Уведомления и escalation (эскалация)
В международных системах есть автоматические **уведомления и эскалация**: просрочка → уведомление куратору → руководителю управления → заместителю акима.

**Предложение:** серверный Frappe Scheduler + уведомления (email/Telegram-бот) с эскалацией по уровням.

### 2.9 Публичность и открытые данные (Open Data)
Подход «Open Contracting» (OCDS — Open Contracting Data Standard) — публикация стадий контракта.

**Предложение:** экспорт данных объекта в **OCDS-совместимый JSON** и публичный «паспорт объекта» на портале (доверие граждан).

### 2.10 Мобильный обход с офлайн-режимом
Инспектор в поле фиксирует осмотр в мобильном приложении даже без сети (офлайн-first, как Fulcrum).

**Предложение:** PWA с офлайн-кэшем для выездных проверок (фото + геометка + подпись).

## 3. Приоритетный roadmap доработок

| Приоритет | Доработка | Ценность для заказчика |
|---|---|---|
| 🔴 Высокий | Поручения в протоколах совещаний (action items) | «Поговорили и забыли» → контроль исполнения |
| 🔴 Высокий | Уведомления и эскалация (Frappe Scheduler) | Просрочка не остаётся незамеченной |
| 🔴 Высокий | Risk Register (вероятность × влияние) | Проактивное управление рисками |
| 🟠 Средний | VAC, TCPI, прогноз даты, S-кривая | Полноценный EVM по PMI |
| 🟠 Средний | RFI / Submittals с SLA | Юридическая фиксация задержек заказчика |
| 🟠 Средний | Модуль «Документы» (CDE со статусами) | Единая среда данных по ISO 19650 |
| 🟡 Низкий | Мобильное PWA с офлайн-обходом | Работа инспектора в поле |
| 🟡 Низкий | Экспорт OCDS / публичный паспорт | Открытость и доверие |
| 🟡 Низкий | Аэрофотосъёмка (дрон) → ГИС | Контроль фактических объёмов |

## 4. Что стоит честно говорить в заявке

- Прототип демонстрирует **основной сценарий** на синтетических данных; перечисленные модули — **дорожная карта пилота**, а не готовые функции.
- EVM и журнал событий в текущей сборке — **демонстрационная реализация логики** на клиенте; серверный расчёт, роли и аудит — этап Frappe-пилота.
- Методология (EVM, ISO 21500/19650, PMI Risk Register) — реальная международная база, на которую опирается архитектура.
